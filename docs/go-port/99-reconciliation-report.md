## 3. Cross-area contradictions

### 3.1 🔴 **The timeout ladder is asserted as total and is not** — A1 + A7 vs A4 F23

> **A1** (`01-bootstrap.md:417,419-420`): case 25 = _"run token TTL **always**
> outlives the configured query window"_; _"Cases 21–25 are a coupled group
> asserting the **timeout ladder**: `PM_QUERY_TIMEOUT` < proxy watchdog <
> `queryExchangeTimeoutMs` < `runStreamTimeoutMs` ≤ run-token TTL."_

> **A7** (`07:425-427`): _"🔒 **INV-A7-30 — the run token must outlive the whole
> exchange it backs** (dial + window + revalidation), else a genuine long query
> fails `UNAUTHENTICATED` when the proxy revalidates the token mid-run."_

> **A4** (`04:1651`, F23): _"`runTokenTtlSeconds = max(900, queryTimeout + 180)`
> (A7) is passed through `clampTtlSeconds`, which caps at
> `TOKEN_MAX_TTL_SECONDS` (24 h), while `Config`'s only bound on
> `PM_QUERY_TIMEOUT` is an overflow guard
> (`MAX_QUERY_TIMEOUT_SECONDS = 9_223_372_006`). A query timeout above ~23 h 57
> m yields a run token that is **silently clamped**…"_

**A4 is right; A1 and A7 are wrong.** Verified end to end this session:

- `RunExec.kt:280` passes `runTokenTtlSeconds` into
  `core.tokenStore.issue(...)`.
- `Tokens.kt:126` — `val ttl = clampTtlSeconds(ttlSeconds)`; `Tokens.kt:81` —
  `coerceIn(TOKEN_MIN_TTL_SECONDS, TOKEN_MAX_TTL_SECONDS)`; `Tokens.kt:76` —
  `TOKEN_MAX_TTL_SECONDS = 24 * 3600L`.
- `Config.kt:138` — `MAX_QUERY_TIMEOUT_SECONDS = 9_223_372_006L`, and
  `Config.kt:189` accepts anything up to it.
- **`ConfigGuardTest.kt:65-79` asserts the pure function only** —
  `RunExecService.runTokenTtlSeconds(timeout) > timeout` — never the value
  actually persisted in `proxy_token.expires_at`. So the test passes at
  `MAX_QUERY_TIMEOUT_SECONDS` while the real token expires 24 h in.

Breakpoint: `PM_QUERY_TIMEOUT > 86,220 s` (86,400 − 180 = 23 h 57 m). **The Go
port must not carry A1's "always" or A7's INV-A7-30 as an unconditional
invariant** — either clamp `PM_QUERY_TIMEOUT` to
`TOKEN_MAX_TTL_SECONDS − TOKEN_TTL_GRACE_SECONDS` at config-parse time, or
assert the ladder on the stored expiry rather than the pure function.

### 3.4 🟡 **Two advisory-lock hash functions share one Postgres lock namespace — neither doc says so**

> **A3** (`03:318-322`): _"🔒 **INV-A3-4 — the lock key must stay
> `hashtext(<principal>)`, computed BY POSTGRES**… `hashtext` is a **32-bit**
> hash, so distinct principals **can** collide — that only over-serializes
> (safe)."_

> **A11** (`11:150`): _"take
> `pg_advisory_xact_lock(hashtextextended(<principal|clientId|toolName|key>, 0))`"_

Verified: `Deprovision.kt:17` uses `hashtext` (returns `integer`);
`mcp/McpServer.kt:257` uses `hashtextextended(?, 0)` (returns `bigint`).
Postgres has one single-argument `pg_advisory_xact_lock(bigint)`, so the
`integer` is widened and **both locks live in the same key space**. Consequence:
an MCP idempotency lock can block a principal teardown. Direction is safe
(over-serialization only, per INV-A3-4's own argument), but a Go port that
"unifies" the two hashes, or that keeps them but uses `(int, int)` for one,
changes which calls serialize. Neither doc records the interaction.
